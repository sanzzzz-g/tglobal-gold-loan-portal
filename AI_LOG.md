## 1. AI Assistant System Architecture & Tool Integration

### 1.1 Goal
Equip the portal with an intelligent, conversational Gold Loan Specialist that can answer customer queries regarding interest rates, tenure, gold purity, valuation methodologies, calculate personalized quotes in real-time, and submit loan applications on the borrower's behalf.

### 1.2 Model Selection & Tool Calling Protocol
- **Model**: `gemini-2.5-flash` via `@google/genai` TypeScript SDK.
- **Location**: Strictly server-side (`server/services/aiService.ts` and `server/routes/ai.ts`). API keys are never exposed to client browsers.
- **Three Core Functional Tools**:
  1. `get_loan_schemes`: Retrieves the authoritative scheme registry (EMI Plan vs Bullet Plan, interest rates, LTVs, tenure limits).
  2. `calculate_loan_quote`: Calls the backend calculation engine with `grossWeight`, `stoneWeight`, `purityKarat`, and `schemeId` to return exact rupee values.
  3. `submit_loan_application`: Calls the transactional `createApplication` service with applicant metadata, gold weights, and mandatory consent.

### 1.3 The Strict Customer Confirmation Safeguard
Financial transactions require strict user consent. A common vulnerability with LLM agents is calling mutation tools prematurely (e.g., user asks "What would I get for 20g 22K?" and the agent immediately submits a loan application without explicit permission).

**Enforced Safeguard**:
1. The AI system instructions explicitly decree:
   > *"CRITICAL RULE: NEVER call submit_loan_application without explicit customer confirmation. If the customer provides gold details and asks to apply, first call calculate_loan_quote, present the quote, and explicitly ask: 'Would you like me to submit this application for you?' ONLY call submit_loan_application if the customer confirms with 'yes', 'confirm', 'proceed', or similar affirmative statement."*
2. If the user affirms, the agent calls `submit_loan_application` with `consentGiven: true`.
3. If the user declines, the agent acknowledges and retains the quote without submitting.

### 1.4 Thought Signature Preservation in Gemini Tool-Call Loops
In modern Gemini 2.5 models, when a function call (`functionCall`) is generated by the model, the SDK returns a candidate with potential thinking/thought parts. When feeding the tool call result (`functionResponse`) back into the model in subsequent turns of the execution loop, failing to retain the original candidate content or altering the role structure can trigger HTTP 400 or malformed turn errors.
- **Implementation**: The recursive tool execution loop in `server/services/aiService.ts` appends the exact model `candidate.content` to `contents`, followed by a `user` role content containing the `functionResponse` part, maintaining pristine session continuity.

### 1.5 Offline Deterministic Fallback Engine
To ensure that evaluators or offline test environments without active `GEMINI_API_KEY` credentials can thoroughly test the AI Assistant without disruption:
- `server/services/aiService.ts` includes an offline rule-based fallback that parses user queries (e.g., regex matching weights, karats, and schemes), invokes the exact same `calculateLoanQuote` backend engine, and provides formatted responses with the confirmation safeguard.

## 2. Financial Calculation Integrity & Reproducibility

### 2.1 Explicit Rules Tested Against Specification
- Reference 24K Gold Rate: **₹7,000 / gram**
- Karat Multipliers:
  - 18K: $18 / 24 = 0.75$
  - 22K: $22 / 24 = 0.9166666666666666$
  - 24K: $24 / 24 = 1.00$
- Net Weight: $\text{Gross} - \text{Stone}$
- Purity-Adjusted Value: $\text{round}(\text{Net Weight} \times 7000 \times (\text{Karat} / 24))$
- Eligible Loan: $\text{round}(\text{Purity-Adjusted Value} \times \text{LTV})$

### 2.2 Preserved Test Cases
All 3 mandatory test cases produce identical figures across the backend calculation engine, the API routes, the frontend UI presets, and the Vitest suite:
- **Test Case 1** (20g gross, 2g stone, 22K, EMI 75%): Net = 18g, Value = ₹1,15,500, Max Loan = **₹86,625**
- **Test Case 2** (50g gross, 0g stone, 24K, Bullet 70%): Net = 50g, Value = ₹3,50,000, Max Loan = **₹2,45,000**
- **Test Case 3** (10g gross, 1.5g stone, 18K, EMI 75%): Net = 8.5g, Value = ₹44,625, Max Loan = **₹33,469**

## 3. Engineering Decisions & Problem Resolutions

| Issue Encountered | Root Cause | Solution Implemented |
|---|---|---|
| **Node.js ESM Type Export Error** | `server/routes/schemes.ts` imported `LoanScheme` directly as a value from `server/types/index.ts`, which compiles to runtime imports in pure Node ESM. | Switched to `import type { LoanScheme }` throughout backend route files. |
| **Zod v3 Enum Syntax Warning** | Using standard mutable array in `z.enum([...])` caused TypeScript strict inference errors. | Added `as const` assertion: `z.enum(['emi_plan', 'bullet_plan'] as const)`. |
| **Vite Dev Middleware Type Incompatibility** | Express app type `(req, res, next)` didn't strictly match Connect's `NextHandleFunction` in Vite's `configureServer`. | Wrapped invocation in `(req: any, res: any, next: any) => app(req, res, next)` adapter. |
| **Mobile Number Normalization** | Indian mobile inputs vary widely (`+919876543210`, `9876543210`, `09876543210`, `+91 98765 43210`). | Created `normalizeIndianMobile()` with regex matching leading `+91` or `0`, ensuring clean 10-digit validation starting with digits 6-9, stored as canonical `+91XXXXXXXXXX`. |
| **7-Day Duplicate Application Collision** | Multiple submissions within 7 days from the same applicant. | Added `checkDuplicateApplication()` query with SQLite `datetime('now', '-7 days')`, returning HTTP 409 Conflict with the existing reference code. |
| **Admin Privacy Violation** | Showing customer phone numbers in plain text in public list views. | Added `maskMobileNumber()` (`+91 98*** **210`) for all admin table responses, while providing the unmasked number only upon explicit detail modal opening by an authenticated admin. |
